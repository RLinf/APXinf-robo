# PI0.5 on A800-SXM4-80GB (SM80)

Build, baseline, and platform notes for PI0.5 on NVIDIA A800-SXM4-80GB
(sm_80, 108 SMs), driver 550.163.01, CUDA 12.9, cuBLAS 12.9, rust stable,
CPython 3.12. Measurements are from a standalone checkout of
`infinigence/ApxInf` @ `95e0af3`, not from this repository's submodule.

## Build

- The build auto-detects the visible GPU and compiles for it; no
  `APXINF_CUDA_ARCH` override is needed for sm_80. Engine main builds
  clean on sm_80; the `apxinf` commit currently pinned here predates the
  non-sm100 GDN link fallback and needs the submodule update.
- The `apxinf_py` wheel resolves `numpy>=1.21`; pin `numpy<2` alongside
  `openpi-client` (which requires `numpy<2`) when using the websocket or
  LIBERO client.
- FP8 is refused up front on this part:
  `PI0.5 model_variant=fp8_static is unsupported on sm_80; it requires
  sm_100 or newer and will not fall back to bf16`.

## Tuning state

Numbers below are from that standalone `95e0af3` checkout after one
`--autotune` run. The run persists per-exact-key `.recipe` caches under
`configs/tuning/nvidia/a800-sxm4-80gb-sm80/cuda12.9-cublas12.9/`
(gitignored by design). On `95e0af3`, a stock checkout without recipes
runs the 2-view BF16 cell at 31.02 ms L1, about 7% slower than 28.73 ms.
The same untuned bench on `c8dd416` was 1948.69 ms. The legacy JSON store
adds nothing on top of the recipes.

## Baseline (warmup 10, samples 30, `H=10`, batch 1, random weights)

Two boundaries per cell: L1 = update already-resized uint8 images,
tokens, and noise + CUDA preprocessing + graph replay + synchronize
(the input-update + graph-replay boundary); L0 = preprocessed patches
input, the closest available proxy for the graph-replay boundary. On
this part the two differ by 0.3-0.5 ms. Three-view rows reuse the wrist
image (duplicated wrist fixture). `T` is the synthetic token count
(`--token-count`); the official fixture prompts only enter the L2
tokenizer path.

| Path | Views | `T` | L0 P50 / P95 | L1 P50 / P95 |
|---|---:|---:|---:|---:|
| BF16 | 2 | 10 | 29.08 / 29.10 | 28.73 / 28.79 |
| BF16 | 2 | 21 | 29.06 / 29.09 | 28.76 / 28.76 |
| BF16 | 3 (duplicated wrist) | 10 | 34.81 / 35.15 | 34.31 / 34.32 |
| BF16 | 3 (duplicated wrist) | 21 | 34.84 / 34.85 | 34.37 / 34.39 |
| INT8 (dynamic W8A8) | 2 | 10 | 59.29 / 59.30 | 58.94 / 58.96 |
| INT8 (dynamic W8A8) | 2 | 21 | 59.33 / 59.36 | 59.04 / 59.07 |
| INT8 (dynamic W8A8) | 3 (duplicated wrist) | 10 | 66.82 / 66.84 | 66.43 / 66.45 |
| INT8 (dynamic W8A8) | 3 (duplicated wrist) | 21 | 66.81 / 66.88 | 66.36 / 66.38 |

One-step action generation (1 flow step), BF16, 2 views, `T=10`:
16.89 / 16.94 ms L1 (59.2 Hz); L0 17.23 / 17.88 ms.

Latency only, random weights; no LIBERO success-rate claim is made here.
The token count enters the computation (actions differ between `T=10`
and `T=40`) but costs below 0.1 ms on this part — `T=21` matches `T=10`
within 0.05 ms on every cell.

Like for like against the README tables, using L0: 10-step BF16 at
2 views (29.08 ms) is faster than RTX 4090 BF16 (31.38 ms) and slower
than RTX 4090 INT8 (25.99 ms in this README; the engine README now lists
21.92 ms). One-step BF16 L0 (17.23 ms) is faster than the published RTX
4090 one-step BF16 (20.36 ms).

## Platform notes

- INT8 (`int8_dynamic`) at batch 1 is 58.94 ms L1 on `95e0af3`, against
  28.73 ms BF16 on the same build and about 29.97 ms for this cell on
  pinned engine `7f37642`. End-to-end INT8 actions stayed finite
  (max abs diff 2.3e-2, mean 3.1e-3 against BF16, action scale about
  3.14). The README table records BF16 only.
- The FA2 split-KV path is active here. L1 P50 is 28.73 ms with it and
  33.78 ms with `APXINF_DISABLE_FA2_SPLITKV` set. End-to-end actions
  stayed finite, with no NaN: max abs diff 1.56e-2, mean 7.9e-4 on the
  task_08-token variant. This is end-to-end only and does not explain
  the 76-SM NaN in infinigence/ApxInf#82.
- `APXINF_DISABLE_FA2_SPLITKV` disables the path when the variable is
  merely present — the value is not parsed (`candidates.cpp` checks
  `getenv(...) != nullptr`); setting it to `0` does not mean "on".
- GDN-bearing models (Qwen-Drive, Qwen3.8 backbones) do not run on
  sm_80: the vendored Cake GDN prefill needs tcgen05, and the operator
  layer does not dispatch the GDN prefill on devices without the kernel.
